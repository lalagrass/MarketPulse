## DO-4　修正虛無分布的抽樣範圍

**背景**

`persistence_null_test` 的位移抽樣是 `s = rng.integers(k, n - k)`，配對索引為
`(positions - k + s) % n`。

- `s = k` 時該索引恆等於 `positions`——**partner 與 current 是同一個矩陣，
  相關係數恆為 1.0**。而 `s = k` 正是抽樣範圍的下界。
- 其鄰域 `s = k ± j` 給出 effective lag `∓j`：lag 1 的持續性約 0.92、lag 5 約 0.71。
  虛無分布因此混入一整段「幾乎沒位移」的抽樣，右尾又肥又高。
- docstring 的理由（「s 取自 `[k, n-k)` 所以永遠不接近 0 或 n，那裡的環繞配對會與真實的
  lag-k 配對重合」）**推理有誤**：與觀測值重合的是 `s = 0`，退化成自我比較的是 `s = k`。
  排除了前者，卻把後者放在範圍起點。

**歸屬：這條來自 sprint 002 的 DO-1（`c2aaefe`），sprint 003 原封不動繼承，
不是本輪引入的。**它同時影響 002 與 003 回報的每一個百分位，方向是**壓低**——
檢定過度保守，真實顯著性被低估。

**規劃端的合成驗證**（730 × 11、AR(1) φ=0.90、複製同一套抽樣邏輯、`seed=0`、`n_iter=1000`）：

```text
              合成      003 實測
k=1           99.9      99.9
k=5           99.3      99.3
k=20          94.9      95.8
null_std   .08-.10   .10-.13
```

k=5 那筆最能說明問題：觀測值高出虛無平均 **6.1 個標準差**，卻只排 99.3 百分位——
還有 7 次抽樣比它高。六個標準差不可能有 0.7% 的機率。查那 7 次的位移量，
**全部是 |effective lag| ≤ 60 的近退化抽樣**。不同資料、同一套演算法、同一組百分位，
代表這些數字主要由抽樣範圍決定，不是資料的性質。

**規劃端跑不了真實資料**（本機無回補資料，容器與本機皆裝不到 `pyarrow`）。
以上是合成證據，實測數字請你自己跑出來。

**做什麼**

1. 抽樣改為：先抽 effective lag `e`，令 `s = k + e`，排除 `min(|e|, n - |e|) < L` 的抽樣。
2. **`L` 不得用「試出來最好」的值（D10）。**用一個講得出理由的定義，理由寫進 docstring。
   兩個候選，自己挑並說明為什麼：`max(2k, 60)`；或「`rank_persistence` 衰減到虛無平均
   以下的最小 lag」。後者自適應但要多算一輪，前者固定但理由較弱。
3. 修正 docstring 裡那段錯誤推理，寫明退化點是 `s = k`。
4. 重跑 `validate-signal`，`k = 1 / 5 / 20`，**新舊數字並列**。
5. 若結論方向改變，更新 `003-report.md`，並在報告中明講前一版的數字為何有偏。

**驗收條件**

1. 新增測試：**任何抽樣都不得使 partner 索引等於 current 索引。**
   這條測試套在修正前的程式碼上**必須失敗**——回報你確認過它會失敗，
   以及失敗時的實際輸出。只會通過的測試不算證據。
2. 新增測試：以人工構造的序列驗證虛無分布不含 `|effective lag| < L` 的項。
3. `k=1` 的健全性檢查仍通過；另外回報 `k=1` 修正後的百分位與虛無標準差
   （**它原本就是靠污染才停在 99.9 的**，修正後應該更極端）。
4. 新舊數字並列表，含 `observed` / `null_mean` / `null_std` / `percentile` / `n_days_used`。
5. **不得因為新數字比較好看就回頭調 `L`。**

**會動到的檔案**：`marketpulse/quality.py`、`tests/test_quality.py`、`docs/sprints/003-report.md`
