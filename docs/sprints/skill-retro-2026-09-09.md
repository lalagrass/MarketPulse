**物證，決定性的一條：**009 驗收之後，skill 加了

還抄了 Gherkin 的自檢問句。**之後 014 犯兩次、015 犯兩次。**

| 輪 | 規劃端寫進 spec 的機制診斷 | 結果 |
|---|---|---|
| 009 | 「`敘事` 是全表唯一沒有欄寬的欄」 | `Momentum` 也沒有，畫面零改變 |
| 010 | 「radar 要能回答資料到哪一天」 | 沒跑過 refresh 時顯示一切正常 |
| 014 | Appetite「只動兩個模組」＋ 前提決定「第三籃收 theme_ids」 | 兩句不可能同時成立 |

這個專案自己引過官方判準（`backlog.md`「開發流程要不要再加 skill」）：
**必須每次發生、不需判斷 → 確定性腳本／hook，不是 skill、不是靠模型自律。**

**而 `scripts/acceptance-check.sh` 2026-09-06 就提出了（`5534918`），至今未做。**
它是唯一擋得住這一整類的東西，卻因為 ENG 永遠擠不進 DO 而一直躺著。

### 決定：016 DO-1，而且做成 hook 不是腳本

[Claude Code hooks](https://code.claude.com/docs/en/hooks) 的 `Stop` 事件
**可以用 exit 2 擋住收工，並把 stderr 的訊息餵回 agent**（官方文件已複驗）。
`PreToolUse` 同樣可 block。所以檢查不必靠人記得跑。

要檢查的全部是機械的、不需判斷的：

```text
spec 側（規劃端收工時）
  1. 每條驗收條件有 WHEN … THEN … 的成對結構
  2. 含目視詞（對齊／一眼／看得出／好懂）的條件，同段必須有
     「目視驗證，貼原文，不得以測試通過為證據」
  3. spec 裡出現的檔名:行號真的存在
  4. spec 裡寫死的統計數字（273 這種）必須標 (量出來的，驗收時重量)
  5. wc -l ≤ 200

實作端側（收工時）
  6. 測試名不得含目視詞
  7. evidence 有真的 N passed in Ns 行
  8. 每個驗收條件代號在 evidence 裡有對應段落
```

```text
條文：機械檢查用 hook，不用規則
起因：009 加了規則，014／015 各犯兩次；acceptance-check 提出三天未做
物證：本節上表六列；backlog 2026-09-06 那則官方判準
重看：017 收尾——若 hook 上線後仍有同類發作，問題不在自律也不在工具
```

## 3. 慢因三：每輪四次人肉搬運，而官方已經有不用搬的做法

**現在的一輪：**規劃端寫 spec → 產出 prompt → PO 貼進 Claude Code →
agent 實作 → PO 把回報貼回來 → 規劃端讀 diff 驗收。**四次複製貼上。**

而且它會直接製造事故。2026-09-09 規劃端為了讀 evidence 在共用工作目錄跑
`git checkout dev`，VM 端刪不掉檔案，結果 HEAD 在 `dev`、檔案內容是 `015`，
`.git/index.lock` 卡住切不回去，只能請 PO 在 Mac 上 `rm -f` 解。

[官方的 parallel-agents 文件](https://code.claude.com/docs/en/agents) 有三樣現成的：

| 東西 | 解掉什麼 |
|---|---|
| [Worktrees](https://code.claude.com/docs/en/worktrees) | 每個 session 自己的 checkout，規劃端與實作端不再互踩同一個工作目錄 |
| [Agent view](https://code.claude.com/docs/en/agent-view)（`claude agents`） | 派工到背景 session、回來看狀態，取代「貼 prompt → 等 → 貼回報」 |
| [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging) | session 之間直接傳結果，含 Claude Code on the web |

**建議只先做 worktree。**它不改工作流程、零學習成本，
解掉的是一整類「兩端踩同一個目錄」的事故。Agent view 與 messaging 先觀察。

**不建議 dynamic workflows。**那是為了「一次做完 500 個檔案的遷移」或
跨 agent 交叉驗證而生；我們的瓶頸是規劃端寫得太快，不是併發不夠。

```text
條文：規劃端與實作端不共用同一個工作目錄
起因：2026-09-09 規劃端 checkout 把工作目錄弄成 HEAD／內容不一致
物證：本節第二段；`.git/index.lock` 需 PO 在 Mac 上手動移除
重看：016 收尾
```

## 4. 這一輪要質疑的規則：不是規則，是規劃端自己

`013-no-sprint.md` §1 已經寫過這句：

> 規劃端連續四輪引用了沒有當場複驗的事實……四次的共同來源是
> **規劃端在讀文件而不是在讀現場**。

**那句話寫在 2026-09-08，然後 014、015 又各犯兩次。**
所以問題不是沒意識到，是**寫 spec 的速度超過查證的速度**。

再加一條規則沒有用（見 §1）。三個可行的：

- **(a) 把驗收條件的數量砍半。**014 有 14 條（F1–F14）、015 有 10 條（G1–G10）。
  條件越多，規劃端推測機制的機會越多——六個矛盾裡有五個出在驗收條件上。
  **提議：每輪驗收條件上限 8 條，超出就是 DO 太多。**
- **(b) spec 自檢前移到開工前。**014 與 015 的矛盾**實作端兩次都自己抓到了**，
  只是在做完之後才講。把「這份 spec 有沒有自相矛盾」變成實作端的第一個動作，
  零成本，而且它命中率 2/2。
- **(c) hook 檢查（§1）。**

**三個都做，順序是 (b) → (c) → (a)。**(b) 今天就能生效，只要改交接 prompt 的第一句。

### 追記（2026-09-09）：第七次，就在這份 retro 裡

本文 §2 原本寫「015 的 `branch` 欄沒有欄寬，是同一個病的第四次」。
半小時後查程式碼：**欄寬存在（`BRANCH_COL_WIDTH = 36`），病灶是 `_ljust` 不截斷。**
又是同一個形狀——**在文件上推理，沒有讀現場。**

**這件事改變了三個做法的排序。**問一次：§1 提議的 hook 檢查會抓到它嗎？
**不會。**hook 能查「檔名:行號存在」「數字標了重量」「WHEN/THEN 成對」，
但查不出「規劃端斷言某個東西不存在，而它其實存在」。

**擋得住這一類的只有 (b)：實作端開工前先讀 spec 並回報矛盾。**
014 與 015 兩次矛盾都是實作端抓到的，命中率 2/2。
**所以 (b) 從第一順位變成唯一真正對症的一項**，(c) hook 與 (a) 條件上限
仍然值得做，但它們解的是別的東西。

### 追記二（2026-09-09，同日）：(b) 第一次執行，一次來回抓到八件

016-spec 交接時第一次把「開工前自檢」放進 prompt。實作端一輪回報：

```text
硬矛盾   1  A1（每條驗收條件要有 WHEN…THEN）× H8（目視條件沒有 WHEN…THEN）
            × H2（本檔八項全過）——三者不可能同時成立
判準缺陷 3  A3 認不出 basename、A4 會誤殺股票代號與日期、A6 會數到 code block 裡的代號
引用錯誤 4  斷點清單的排序歸因（實際是 baskets.py:466 依 (date, symbol)，不是 YAML 順序）、
            「超過 200 字元」實測 317、retro 的 §4a 節號不存在、H5 的措辭按字面驗不過
```

**其中 hook 查得到的只有一項（A3 的 basename）。**歸因錯、措辭錯、判準互斥，
機械檢查全部查不出來。

**兩個直接後果：**

1. **A4 從檢查清單刪除。**它要抓的是「把量出來的數字寫死」，而這一次實作端
   不靠腳本就抓到了 `273`。留一支會誤殺股票代號的檢查器，代價是它會被忽略——
   **一支會亂叫的檢查器比沒有更糟。**
2. **A1 不開「目視條件」的例外，改寫 H8。**例外在規則上線第一天就開，
   等於沒有規則。H8 改成 `WHEN 一條支線同時有三行數字、斷點清單與提示
   THEN 那三行仍讀成一個整體` ——目視條件一樣寫得出 WHEN／THEN。

```text
條文：實作端開工前先回報 spec 的矛盾與引用錯誤，規劃端答覆後才動工
起因：014／015 的矛盾都是實作端事後才講
物證：016 首次執行，一次來回八件，其中七件 hook 查不到
重看：018 收尾——若某一輪自檢回報「沒有問題」而事後仍出現矛盾，這條要重新設計
```

**這是第八次。**規劃端在寫「連續七次」的那份 spec 裡又犯了四次引用錯誤。

**第二輪自檢：修正本身帶進了新的矛盾。**改完之後再跑一次，實作端抓到
`H1` 還在引用已刪除的 `A4`（**規劃端修 bug 時製造的**），外加四處沒跟著改的
交叉引用（兔子洞、明確不做、`H2` 的「八項」、物證的「應只有一格」）。

```text
條文（補強）：自檢跑到收斂，不是跑一次。規劃端改完 spec 之後要再交回自檢一輪
起因：016 第一輪的修正引進了 H1→A4 這個新的硬矛盾
物證：016 第二輪回報第 1 項
重看：018 收尾
```

**兩輪合計十三件，硬矛盾兩件，兩件都是規劃端在修東西的時候製造的。**
這條數字本身就是 §4 (b) 值不值得的答案。

```text
條文：實作端開工前先回報 spec 的自相矛盾，規劃端答覆後才動工
起因：014 Appetite／前提決定衝突、015 G6／G7 衝突，兩次都是實作端事後才講
物證：014-report §3.1、015 回報第 2 段
重看：017 收尾——若前移之後矛盾仍在事後才被發現，這條無效
```
