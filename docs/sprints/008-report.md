## 四、規劃端自己讀 diff／重算查到的四件事

### F4 — `敘事` 是全表唯一沒有欄寬的欄（F3 只治了表頭）

規劃端自行重算顯示寬度：

```text
表頭（含 敘事）        110   ← 分隔線現在等於這個
資料列結尾 "  —"       107
資料列結尾 "  2026-09-06" 116
舊寫死值                114
```

**分隔線對得上表頭，對不上任何一種資料列。**真正的缺陷不是分隔線的數字，是
`敘事` 欄沒有欄寬——其他每一欄都有（`{'RS20':>7}` 等），只有它是直接接在後面，
所以表格右緣是參差的。**F3 照 spec 做對了；限制在 spec —— 我只叫它對表頭，
而表頭不是最寬的列。**正解是給該欄固定欄寬（10 ＝ ISO 日期寬）。→ 建議進 009 或順手修。

### F5 — `declared` 是「宣稱」，不是「已驗證」

`coverage_report()` 只要 `theme_ids` 非空就回 `declared`（`narratives.py:329`），
**不檢查那些 id 存不存在**；而 `_mentioned_theme_ids()` 會把不存在的 id 全部丟掉。
於是一則 `theme_ids` 全部打錯字的 narrative，`coverage_report` 說它 `declared`，
覆蓋計算卻說它什麼主題都沒提到——**兩個函式對同一則給出相反答案。**

今天踩不到（唯一的 `theme_ids` 值是合法的 `optical_cpo`），而且未知 id 有訊息會喊。
但 `declared` 這個字現在的意思是「它宣稱了」，不是「它宣稱的東西存在」。→ backlog。

### F6 — 成員資格測試現在有兩份實作

007-spec 明令「覆蓋判定用既有的 `coverage_report()`，**不要自己重寫一套主題↔標的比對**」。
008-spec 沒有重申這條，於是 `theme_mention_dates()` 從「呼叫 `coverage_report()`」
改成呼叫新的 `_mentioned_theme_ids()`，而後者自己實作了一次 `named & members`。
兩份實作各自獨立，docstring 聲稱「same test」——**聲稱不是保證，改一邊另一邊不會知道。**
→ backlog：讓 `coverage_report()` 建立在 `_mentioned_theme_ids()` 之上，或反過來。
**這條是我漏寫，不是實作端違規。**

### F7 —（最重要）008 今天的使用者可見效果是零

規劃端查了資料狀態：`data/raw/{TWSE,TPEx}` 都停在 **20260903**（週四）。
narrative 檔是 09-04 與 09-06。PIT 規則（`snapshot_date <= as_of`）因此讓真實
`brief`（as_of=2026-09-03）拿到**空快照**，於是：

- DO-1 的頭號驗收（光通訊/CPO 離開「強但沒人講」）**在真實輸出裡看不到**——
  覆蓋為空，它照樣被列為沒人講。
- DO-2 的兩個新區塊、DO-1 的 `分類外代號`，**全部被 gate 掉，一個都不出現**（見 B1）。
- evidence 裡每一段「真實 narrative」輸出都標了反事實，**標注是誠實的**——
  但把三段反事實加起來，結論是：**這一輪交付的東西，使用者今天一樣都摸不到。**

**這不是實作端的問題，是資料落後三天。**2026-09-04（週五）是唯一沒下載的交易日；
09-05／09-06 是週末無盤。跑一次 `refresh` 之後 as_of=09-04，
`narratives/2026-09-04.yaml` 就進得來，`分類外代號`（`asic_xpu · 2454`）與
`敘事` 欄（先進製程 ← `nvhbm` 的 2330）會真的亮起來。

**但 DO-1 的頭號效果還是要等到週一。**`theme_ids` 只寫在 09-06 那份檔裡，
而 `as_of` 最多只能到 09-04（週五）——**2026-09-07 的價量資料落地之前，
`load_as_of` 永遠看不到 09-06 的快照。**

**由此得到一個沒人寫過的產品事實：週末寫的 narrative，在下一個交易日的資料落地之前
完全不可見。**這不是 bug，是 PIT 規則在做它該做的事；但「我寫了，畫面沒反應」這個
007 診斷出來的核心問題，**有一部分的成因是這個**，而 007 與 008 都沒處理到它。
