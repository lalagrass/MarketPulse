## §0.1 DO-2 的成因：不是檔位進位，是浮點比較

`011-evidence.md` 印出 1909 筆「不可能的單日報酬」。逐行統計：

```text
grep -cE '^\s+[0-9]{4}-[0-9]{2}-[0-9]{2}\s+[0-9]{4}' docs/sprints/011-evidence.md
  → 1909
grep -cE '^\s+[0-9]{4}-[0-9]{2}-[0-9]{2}\s+[0-9]{4}.*[+-]10\.0%' docs/sprints/011-evidence.md
  → 1640            （85.9%，印出來恰好是 ±10.0%）
```

規劃端直接從 `data/raw/TWSE/*.json` 取收盤價回算三筆（未經 `normalize`，未經 parquet）：

```text
1504 東元   2025-04-02 收 49.5    → 2025-04-07 收 44.55
            49.5 × 0.9 = 44.55，44.55 落在 10–50 帶的 0.05 檔位上 → 合法跌停價
1504 東元   2025-07-31 收 51.0    → 2025-08-01 收 56.1
            51.0 × 1.1 = 56.10，56.10 落在 50–100 帶的 0.10 檔位上 → 合法漲停價
6442 光聖   2026-01-26 收 1300.0  → 2026-01-27 收 1430.0
            1300 × 1.1 = 1430.0，1430 落在 ≥1000 帶的 5.00 檔位上 → 合法漲停價
```

三筆的 |r| 在數學上**等於** 0.10。但 `calc.py:155` 是

```python
hits = frame.loc[frame["return_1"].abs() > limit].copy()
```

而在 IEEE-754 下：

```text
abs(44.55/49.5   - 1) > 0.10  →  True
abs(56.1 /51.0   - 1) > 0.10  →  True
abs(1430 /1300.0 - 1) > 0.10  →  True
```

**結論：那 1640 筆不是市場現象，是拿浮點比率去比十進位門檻的產物。**

**因此 `calc.py:41-43` 的註解是錯的。**它寫

> False positives (IPO first five days, **tick rounding that lands just over the
> line**) are listed as-is.

漲停價是**無條件捨去**到檔位、跌停價是**無條件進位**，捨去／進位之後的比率
只會 ≤ 10%，**不可能超過**。檔位進位不會製造這一類偽陽性。
`011-report.md` §2.1 的分桶說明（`0.10 < |r| ≤ 0.101  1644  ← 漲跌停 × 檔位進位，86%`）
沿用了同一個錯誤歸因。**兩處都在 012 一併更正。**

**這不減損 011。**DO-1 的三個驗收條件（指名 6669、全樣本掃描、不改既有數字）
都真的達成了，1644 那個桶的**筆數**也是對的——錯的只有那個桶的**成因**，
而它是規劃端在 spec 裡先寫下、實作端沿用的。

## §0.2 為什麼還是要那張檔位表

只修浮點比較（例如改成 `>= limit + eps`）會清掉那 1640 筆，但仍然是簡化版規則。
真正的漲停價不是 `前收 × 1.1`，是它**無條件捨去到檔位**之後的價格：

```text
前收 9.98（0.01 檔位） → 9.98 × 1.1 = 10.978
                        → 跨進 10–50 帶，檔位 0.05 → 漲停價 10.95 → 實際上限 +9.72%
```

也就是說在某些價位帶，合法漲停的報酬**明顯低於** 10%，而 `> 0.10` 這條線會漏掉
介於實際漲停價與 10% 之間的異常。用檔位表同時解決兩件事：偽陽性與這個漏網區。
這正是 `011-report.md` §6 規則質疑的結論「用規則的完整形式，不要用它的簡化版」——
本輪為它補上第三句：**規則的算術也要用它自己的（十進位價格與檔位，不是浮點比率）。**

## §4 DO-3　官方休市表

### §4.1 規劃端 §0.3 之後才查得到的兩件事

**一、`yy=` 參數是無效的。**這個端點忽略試過的每一種年份參數，永遠回當年度，
並在 `queryYear` 說自己是哪一年：

```text
?response=json&yy=2025        → queryYear 2026  title 115 年市場開休市日期  first 2026-01-01
?response=json&yy=114         → queryYear 2026  ...                        first 2026-01-01
?response=json&queryYear=2025 → queryYear 2026  ...                        first 2026-01-01
?response=json&year=2025      → queryYear 2026  ...                        first 2026-01-01
（舊路徑 /holidaySchedule/holidaySchedule?queryYear=114 亦同；
 openapi.twse.com.tw/v1/holidaySchedule/holidaySchedule 同樣只有 2026，
 日期是 ROC 格式 1150101）
```

TPEx 的 `bulletin/tradingDate?year=2025` 一樣回 115 年，而且把表格塞在
JSON 裡的 HTML 字串。**所以過去年度取不到，快取只能從現在開始累積。**
程式因此以 payload 自稱的 `queryYear` 當快取檔名，不用我們要求的年份
（`test_fetch_is_cached_under_the_year_the_payload_claims`）。

**二、這張表同時列出休市日與它旁邊的交易日。**27 列裡有 3 列是交易日：

```text
  2026-01-02  國曆新年開始交易日      ← 有交易
  2026-02-11  農曆春節前最後交易日    ← 有交易
  2026-02-23  農曆春節後開始交易日    ← 有交易
  2026-02-12  市場無交易，僅辦理結算交割作業  ← 休市
```

把每一列都當成休市，會把真正的交易日標成假日。判準：名稱含「交易日」
且不含「無交易」→ 交易日，不計入休市（`parse_holiday_payload`，
`test_settlement_only_row_is_a_closure_and_trading_rows_are_not`）。
27 列扣掉 3 列交易日 = **24 個休市日**。

### §4.5 驗收條件「N 明顯小於 32」：**沒有達成，照實報**

```text
靠 mtime 才判得出來的日期共 18 天
```

18 < 32，但不是 spec 想要的「少數幾天」。原因不是實作取捨，是 §4.1 那件事：
TWSE 只給當年度，2025 那 18 天的官方表**現在取不到，以後也取不到**。
它們維持 011 的 mtime 判定，並且在畫面上寫明是 mtime 判的：

```text
2025-01-01  官方休市（依 mtime，該年度無官方表）  ← 依 mtime
...
本次判定未使用官方休市表的年份：2025（TWSE 端點只提供當年度；這些日期退回 011 的 mtime 行為）
```

2026 這一側達成了 spec 的目標：14 個空日期裡 **13 天由官方表判定、完全不看
mtime**，剩下的 2026-07-10 是明講的未知。從 2026 起每年會多一份快取，
分母只會往下走。

### §4.6 抓不到官方表時的行為

`test_calendar_fetch_failure_falls_back_and_says_so`：`fetch_json` 丟例外時，
`HolidayCalendar.available` 為 False，判定退回 011 的 mtime 行為，且輸出多一行
「本次判定未使用官方休市表」。不是靜默退回。

`test_cached_calendar_is_not_refetched`：快取檔存在時 `fetch_json` 的呼叫次數
為 0（`refresh` 每年最多抓一次）。

## §5 未決問題的答案與越界紀錄

**未決問題 1（檔位表放哪）。**放在 `calc.py` 的 module-level 常數，不開
`marketpulse/exchange.py`。理由：DO-3 的日曆最後沒有跟檔位表共用任何東西——
它是一個要走 HTTP、要落快取檔的東西，屬於 `data.py`；檔位表只有 `calc.py`
的漲跌停判定會用。開第三個模組只會讓兩個互不相關的常數共處一室（D9）。

**未決問題 2（殘留 300 筆以內是估計）。**實際 273 筆，逐筆全貼在 §3.5。
沒有為了對上任何數字加過濾。

**未決問題 3（`說明` 欄要不要存）。**存。快取檔就是官方回應原樣，
`說明` 自然在裡面；解析器只讀 `日期` 與 `名稱`。

**spec 沒要求、但本輪一併做了的事**（三件，都在報告裡另外列一次）：

1. **表頭補一格前導空白。**DO-1 只寫「給 Momentum 一個固定欄寬」，但驗收要求
   分隔線長度等於**資料列**寬度。資料列有 status mark 欄、表頭沒有，不補這一格
   兩者永遠差 1。
2. **`--no-narratives` 的分隔線由 100 改成量出來的 131。**008 的註解說留著 100
   是為了保住 007 的 sha1；DO-1 既然改了 Momentum 欄寬，那份 sha1 本來就會變，
   而 100 已經比資料列短 31 格。
3. **`parse_holiday_payload` 排除交易日列、快取以 `queryYear` 命名。**兩者都不在
   spec 裡，因為規劃端 fetch 時沒撞到（§4.1）。不做的話這張表會判錯。
