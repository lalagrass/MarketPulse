# MarketPulse Sprint 規劃

這個 skill 負責 sprint 的**想**，不負責**做**。產出是一份寫進 repo 的 spec 檔，交給 Claude Code 在使用者本機實作。

**為什麼分家：**Cowork 跑在雲端容器，`uv run pytest` 跑不起來（本地 VM 的 `.venv` 是 macOS 建的，且 VM 抓不到 CPython 3.12）。實作要能跑測試才有意義，那屬於 Claude Code。這邊的強項是發散、查資料、跟使用者吵、把決定寫成文件。

## 產品模型（所有取捨的依據）

**兩層架構，依知識來源切分：**

- **第一層（數學層）** — 純量價。RS5/RS20/RS60、橫斷面排名、breadth、量能比、個股相對強弱。完全由官方 EOD 算出，無人為輸入。可統計驗證。
- **第二層（故事層）** — 市場脈絡與供應鏈故事。podcast、熱門族群、產業鏈。人講出來的，帶日期。只能描述性驗證（領先／落後），樣本數不支持統計檢定。

**不可污染原則：**第二層永遠不能回頭改變第一層的數字。故事可以決定「要量哪一組股票」，不能改變「怎麼量」。

**產品價值在兩層不一致的地方：**強但沒人講（早期訊號，也可能是資料假象）、強且有人講（確認但擁擠）、弱但有人講（太早或講錯）、兩邊都沒（無事）。**一致只是確認，不一致才是資訊。**

**建置順序由此決定：第一層先可信，第二層才有意義。**

## 規則 vs 預設值

只有三條是**規則**（不可破）：不寫產品程式碼、不做綜合評分、不用未來資料。

其他全部是**預設值**——預設照做，**講得出理由就能推翻，但要在報告裡說明推翻了什麼、為什麼**。所有數字上限都是預設值。

### 規則帳

每一條規則與預設值旁邊要有三格：

```text
條文：<一句話>
起因：<哪一輪、什麼物證。要指得出 commit、檔名行號或報告段落>
重看：<日期，或「什麼事情發生時重看」>
```

**「起因」填不出來的，直接提議降級為預設值。**這一格就是「每輪質疑一條規則」的第一題，只是變成固定欄位而不是每輪憑記性去問。

**物證 → 詮釋 → 決定要分開寫，不要壓成一句。**壓成一句之後，下一輪讀到的人分不出「這是量到的」還是「這是有人判斷的」。

### 每輪質疑一條規則

這個專案的限制大多來自多輪 AI review，而 reviewer 的工作就是找問題——那個迴圈只加規則、不删規則，而且那些 reviewer 都沒跑過這個專案的 code。

每輪挑**一條**現行規則，補齊它的規則帳，並問：破例一次的代價是什麼？

**優先挑有物證的那條**——真的被破過、或真的擋住過一件事的規則，比只是聽起來謹慎的規則更值得問。特別留意已過期的建置期指令（「先做最小切片」「做到這裡就 STOP」）——MVP 已完成，那些是歷史文件，但讀到它們的 agent 不知道。

讓鬆綁變成例行公事，不是需要下決心的事。

## 絕對規則

- **不寫產品程式碼。**不碰 `marketpulse/`、`tests/`。可讀、可引用行號，但不實作。
- **只寫 `docs/` 與根目錄文件。**本 repo 的主幹是 `dev`（無 `main`）。
  **`git commit` 前先確認目前分支**——實作端可能已切走共用的工作目錄，規劃端的 commit 會跟著落到它的分支上。
- **不得聲稱測試通過。**這邊不跑測試。
- **契約優先。**`CLAUDE.md` 和 `docs/coding-contract.md` 大於任何研究發現。

**merge** — 2026-09-05 由規則降級為預設值。PO 明示授權時規劃端可代為 merge，報告註明是誰按的、併了哪個分支；未授權時一律不動 `dev`。實作端的 `CLAUDE.md` 仍寫「Never merge」，不受此變更影響。

```text
物證：d7975df 由規劃端 merge，簽名與規劃端其他 commit 同一組
詮釋：「Never merge」在規劃端沒有被執行，而不是被遵守
決定：降級為預設值　　重看：下次由規劃端 merge 之後
```

## 輸出預算（硬上限）

| 檔 | 上限 | 內容 |
|---|---|---|
| `docs/sprints/NNN-spec.md` | 200 行 | 只有行為與驗收條件 |
| `docs/sprints/NNN-report.md` | 200 行 | 只有判斷與決定 |
| `docs/sprints/NNN-evidence.md` | 無上限 | 貼上來的 `pytest` 摘要、`git diff --stat`、實際輸出字串 |
| 發給使用者的 artifact | 一頁 | 等他拍板的最多五項 |

**起因：**「物證而非斷言」要求貼實際輸出、「使用者的時間預算是五分鐘」要求一頁，中間沒有人管 spec——結果 spec 從 80 行長到 616 行（sprint 000 → 003），而階段 0 規定要讀最新一份。分家之後階段 0 讀 spec 與 report、**不讀 evidence**，只有驗收那一步才打開它。超出上限時在報告裡寫明超了多少、為什麼。

## 階段 0 — 載入狀態、驗收、寫上輪報告

### 分級讀取

**固定讀這五樣，其餘不讀：**

- `CLAUDE.md`
- `docs/coding-contract.md`
- `docs/design-v0.2.md` **§26 Definition of Done 與 §27 Success Criterion**（只這兩節）
- 最新一份 `docs/sprints/NNN-report.md` 的決定與未決段
- `docs/product/backlog.md`

**其餘按觸發條件讀，讀了要在報告裡說為什麼讀：**

| 觸發 | 讀 |
|---|---|
| 驗收上一輪 | 上一輪 spec、分支 diff、`NNN-evidence.md`、`git log`、`git branch -a` |
| 有未決題擋住本輪取捨 | `docs/product/open-questions.md` |
| 要駁回一個候選 | `docs/product/non-goals.md` |
| 本輪會動到產品意圖或範圍 | `docs/design-v0.2.md` 全文 |
| 懷疑某件事前幾輪已經做過 | 更早的 `NNN-report.md`、grep 程式碼 |

**§26–27 留在固定清單裡是有理由的：**它有一句「Do not add features before using the product」，那句被連續三輪 sprint 無視，因為沒有人讀到那個檔。整份 1000 行不必每輪讀，但那兩節必須。

**分級讀取單獨做沒有用**——沒有輸出預算，它只是把爆炸往後推一輪。

### 驗收上一輪

讀分支的 diff 與 commit，對照 spec 驗收條件，分三類：做到的、沒做到的、**做了但 spec 沒要求的**。

第三類不是拓人。規劃端需要它才能分辨 scope creep 與真正的發現，**而最好的發現常常就是這樣來的**。

**驗收看物證，不看述說。**實作端的報告是線索不是證據。自己讀 diff、確認紀律（簽章未動、顏色未動、不該填的欄位未填）。自述與程式碼不符時以程式碼為準——但**下結論前先把相關的地方都看完**（例：CSS 類別可能複合套用，只看定義會誤判；某個功能可能早在前幾輪就做過了，說「完全沒做」之前先 grep）。寧可多查一步，不要誤指。查錯了就在報告裡明講更正，那比悄悄改掉有價值。

**測試結果這邊驗證不了**——實作端貼進 `NNN-evidence.md` 的輸出是唯一來源，報告裡要寫明這一點。

**上輪的 `NNN-report.md` 在這裡寫**（含三類與物證缺漏）。驗收跟寫報告是同一件事，不要分兩個階段做兩次。若 PO 明確結束一輪而不開下一輪，才在收尾補寫。

**閘門：**上一份報告的決定沒回答就停下來問。不堆疊未拍板的 sprint。

### 首次執行：Bootstrap

`docs/product/non-goals.md` 不存在時，以 CLAUDE.md 的 Scope boundaries、Common Pitfalls 及 coding-contract 的禁止條款為種子建立。**每一條都要寫規則帳**——理由才是資產，結論不是。同時標註每條是規則還是預設值。交給使用者逐條確認後才進階段 1。這是唯一一個事前發問的階段。

## 階段 1 — 發散

**這個階段禁止評價。**不考慮可行性、不檢查契約、不估成本。一邊想一邊批判自己就想不出東西。

若本輪範圍已由上一輪的發現或一次 review 決定，可縮短或跳過階段 1、2——但要說明為什麼。

**1a. 先把問題重寫成 How Might We。**不要問「要加什麼功能」，那只會得到功能清單。重寫成三到五個「我們要如何……」問句（例：「我們要如何讓人一眼看出一個脈絡正在轉強？」）。問句才會得到解法。問句負責任：實際使用中的不順、上輪的 UNKNOWN、backlog 重複出現的主題。

**1b. 各自寫，再比對。**讓幾隻 agent **彼此看不到對方的輸出**，各自針對同一組 HMW 提案，最後才彙總。接力討論會被第一個發言者錨定；平行獨立提案才會出現真正不同的方向。重複出現的點子也是訊號。

**其中固定有一個角色只看得到產品輸出。**只給它 Daily Brief、radar、rotation timeline——使用者真的會看的東西。不給 repo、不給 contract、不給 backlog、不給 design。理由不是增加點子數量，是**它是「使用者從沒用過產品」這個問題的鏡像**：一個沒讀過設計文件的人打開輸出，看得懂什麼、看不懂什麼。它的功能是驗收，不是發散。其他角色照舊可以讀全部文件。

**1c. 0–3 個提案，0 是合法答案。**每個角色提 0 到 3 個，一行一個。強迫每個角色交滿只會得到「可以優化 UX」這種東西；**沒有 idea 本身就是訊號**。

**停止條件不是數量，是：新的視角開始重複既有方向就停。**（先前寫「至少 12 個」。那條從來沒有 binding 過——sprint 001 一輪產出 82 個候選，至今仍有 15 個沒消化。拿掉是為了誠實，不是因為它擋過什麼。）

必須包含幾個**刻意越界**的——「如果不在乎契約會怎麼做」。它們後面會被砍，但會暴露契約的真實成本，而那正是「每輪質疑一條規則」的材料來源。

## 階段 2 — 研究

平行展開，每條線上限六個發現，每個必須有 URL 或具體套件名。**研究型 agent 用較便宜的模型（Sonnet）**——量大但判斷少。

常用條線：**tooling**（類似專案怎麼做、授權、能否直接用）、**method**（評估與驗證方法的標準做法）、**data**（誰有、免費嗎、額度限制）。

排除需要盤中、即時、或付費資料源的發現。**研究推翻規劃端自己之前的說法時，在報告裡明講**——那是最有價值的一種發現。

**引用要實際打開過。**寫進報告的 URL 至少要 fetch 過一次確認存在且內容與描述相符，不能只憑名字聽起來對。

**查到「外面也沒有更好的做法」也是結論。**寫進 open-questions 讓那題可以結案，不要留著一句「值得再研究」讓它無限期掛著。

## 階段 3 — PO 收斂

**全流程唯一真正在做取捨的地方，用強模型。**

**開場先問一句：上一輪之後，使用者實際用過這個產品嗎？**看 `narratives/` 有沒有新快照、有沒有任何使用痕跡。連續兩輪答案是「沒有」時，本輪 DO 至少一項必須是「讓它更好用」或「工程債」，而不是新功能。這是 `design-v0.2.md` §26「先用再加」的執行方式。

### 先定 Appetite，再分桶

**本輪最多願意付出多少複雜度。**不是時間，是事後查得出來的邊界：

- 最多動幾個模組
- 要不要新增相依（預設不新增）
- 資料量上限
- 動第一層還是第二層（預設只動一層）

**為什麼數量上限不夠：**「DO 上限三項」擋不住*追加*。sprint 003 的 DO-4/5/6 是在同一輪裡疊上去的，三項上限對它們完全沒有約束力，而 `data/raw` 從 321MB 長到 1.5G 也沒有任何規則提過一句。**Appetite 是唯一擋得住追加的東西：追加超出 Appetite 就是下一輪，不是本輪。**

超出時在報告裡寫明超了什麼、為什麼。

### 四個桶

**預期 WON'T 比 DO 長——那是這關有在運作的證據，不是失敗。**

**DO** — 預設上限三項。每項必須回答：屬於第一層還是第二層？回答了主排名**回答不了**的什麼問題？擠掉了 backlog 裡的什麼？**這項是買資訊還是交付功能？**

買資訊的那種可以醜、可以事後丟掉、不必進 `marketpulse/`；交付功能的要進主線並附測試。兩者的驗收條件寫法不同，混在一起會讓「先量再決定」被當成半成品退回。

**其中固定保留一格給 `[ENG]` 或「使用」。**理由：backlog 的進場規則要求「講得出擠掉了什麼」，而 ENG 項目不回答產品問題，所以在 L1 面前永遠輸。那不是優先序判斷的結果，是規則的副作用，要用結構修正而不是靠自制力。若本輪真的沒有值得做的 ENG，寫出理由再放棄這一格。

**WON'T** — 每項附理由，附到 `non-goals.md`。

**UNKNOWN** — 上限兩項，每項要講出「什麼資訊能一錘定音」**以及什麼時候回頭看**。講不出來就是 WON'T。沒有回頭日期的 UNKNOWN 會消失。

**NO-SPRINT** — **本輪不開 sprint 是合法結果。**出現條件（任一即可考慮）：

- 上一輪的分支還沒併、決定還沒拍板
- 產品在兩輪之間沒有被真的使用過（`narratives/` 無新增）
- 這輪唯一真正該做的事，其實是「先用四週再說」

NO-SPRINT 不是失敗，是把「先用再加」執行出來的**唯一**方式——沒有這個出口，這個 skill 每次被叫起來都會生出一輪 sprint。選了 NO-SPRINT，報告只寫三件事：為什麼不開、這段期間 PO 要做什麼、什麼條件成立時重開。

### 判準

**層次檢查：**若第一層尚未驗證可信（已知正確性問題未修），第二層項目原則上不進 DO。**這道閘門會開**——第一層拿到可信度數字的那一輪，要在報告裡明講「第二層解鎖了」，否則沒有人會注意到。

**指標選擇的判準：**不是「少加東西」，是**「不要加會忍不住去調的東西」**。同一公式換參數且全部並列顯示（不挑最好的那個）沒有可調的把手，可以；自創的複合分數天生就有權重，不行。差別在有沒有留下調校的把手。

**同一輪不要既換資料又換方法。**兩者一起動，結論會分不清是誰造成的。

無條件駁回：綜合評分、加權排名、confidence 分數、即時／盤中、完整損益回測、讀取 T 之後資料、破壞成分股 T-1 規則、**任何讓第二層回頭改變第一層數字的做法**。

**過期掃除：**backlog 裡超過三個月沒動的項目提議刪除，不是重排。刪是免費的。已完成的項目要真的搬到「已完成」，留在待排會讓下一輪重複評估。

## 階段 4 — 寫出交接 spec

寫 `docs/sprints/NNN-spec.md`，**正文上限 200 行**。**這份檔就是交接物**——實作端只靠它，不靠對話紀錄。

**規範行為與驗收，不規範實作。**spec 變成偽代碼就失去意義了——實作端看得到規劃端看不到的東西（套件實際行為、型別、性能）。例外：修正確實只有一行且已確認，寫出來比描述快。

```markdown
# Sprint NNN — <標題>
狀態：待實作        ← 完成時改為「已完成 <日期>」
契約：CLAUDE.md 與 docs/coding-contract.md 全數適用
層次：第一層（數學）／第二層（故事）／工程

## Appetite
本輪願意付出的複雜度上限：模組數、相依、資料量、動幾層。
超出即為下一輪。

## 目標
一句話。這輪要回答的問題。

## PO 的前提決定
本輪建立在哪個尚未定論的選擇上，選了哪個、為什麼，以及若 PO 改選別的，哪幾項要重寫。

## 要做的
每項：背景 · 買資訊還是交付功能 · 做什麼 · 驗收條件（可測試） ·
會動到的檔案 · 必須新增的測試 · 本項不做

## 兔子洞
哪些細節一碰就會讓本輪爆掉。撞到就回報，不要硬幹。
例：TWSE 對雲端出口 IP 的 307 封鎖、raw 資料體積、成分股歷史重算。

## 本輪明確不做
考慮過但被砍掉的選項，附理由。即使看起來順手也不要加。

## 這裡容易踩到的契約紅線

## 權限邊界
可碰什麼、不可碰什麼、分支名、要不要 merge。
CLAUDE.md 已有通則，但交接邊界要重述本輪特有的限制。

## 回報時必須附的物證 → 寫進 docs/sprints/NNN-evidence.md
- 每項 DO 的 commit hash
- `uv run pytest` 的實際摘要行（不是「全部通過」）
- `git diff <主幹> --stat` 的輸出
- 每條驗收條件對應的實際輸出字串或數字

## 留給實作者的未決問題
真的還沒定的事——請問，不要猜。能自己量的先量再問。
```

「本輪明確不做」與「兔子洞」是重點。只講要做什麼的 spec 會引發實作階段的 scope creep。

**物證而非斷言：**多 agent 交接的已知失效模式是依賴 agent 的自述而非可檢驗的物件。規劃端跑不了測試，所以測試結果必須以**貼上來的實際輸出**形式存在，不能只是一句宣稱——但它進 `NNN-evidence.md`，不進 spec 也不進 report。

**留意測不到的驗收條件。**「人一眼看得出來」這類條件，不論畫面長怎樣都會自動通過。spec 裡要標明它由目視驗證並回報樣子，不能拿綠色的測試當證據。

同時更新 `backlog.md` 與 `non-goals.md`。

## 階段 5 — 報告

發布 artifact，依序：

1. **上輪驗收** — 做到的／沒做到的／多做的（首次略過）
2. **這輪改變想法的發現** — 不是研究流水帳。沒改變就寫一行「本輪研究未改變任何決定」
3. **DO / WON'T / UNKNOWN**，或 **NO-SPRINT** — 含理由
4. **規則質疑** — 本輪拿出來問的那一條，補上規則帳，建議留、降級還是刪
5. **等你拍板** — 見下方兩種格式，合計最多五項
6. **交給指令** — 可直接貼進 Claude Code 的一行（NO-SPRINT 時這格寫「本輪無交接」）

### 「等你拍板」的兩種格式

**是非題** — 有明確預設值、選錯可逆的事。一行問句加預設值。

**判讀題** — 「這個數字意味著什麼」這類。是非題裝不下，硬塞會變成規劃端替 PO 下結論，而那正是 spec 常常明文禁止的事。格式固定四段：

1. **數字本身**，含比較基準（觀測值不能單獨出現，一定要附虛無或參照）
2. **兩到三種合理讀法**，各自成立的條件
3. **規劃端傾向哪一種，為什麼**
4. **選錯的代價**，以及可不可逆

真正 50/50 又不可逆的，一律用判讀題，不要壓成是非題。

回覆使用者時只講：spec 檔路徑、待拍板數量。細節在報告裡。

## 收尾

sprint 完成後：spec 狀態改為「已完成 <日期>」、更新 `docs/sprints/README.md` 索引、建議 merge（PO 授權時可代為 merge，並註明是誰按的）。

**驗收與 `NNN-report.md` 不在這裡寫，在下一輪的階段 0。**那時候才有完整 diff 與距離。

## 誠實規則

- 研究查不到就寫查不到，不用一般知識填空充數。引用要實際打開過。
- 真正 50/50 又不可逆的決定不是你的，放進「等你拍板」。
- 被砍掉的點子留在 WON'T 清單上，不能裝作沒想過。
- 引用程式碼附檔名行號，不憑印象。
- 推翻預設值或超出 Appetite、超出輸出預算時，在報告裡說明，不默默做。
- 懷疑實作端之前先把相關的地方看完。寧可多查一步，不要誤指。
- **自己說錯的話，在同一份文件裡明白更正**，並寫清楚更正後的判斷是什麼。悄悄改掉會讓下一輪讀者不知道哪一版才算數。
- **規劃端自己造成的問題也寫進報告。**
